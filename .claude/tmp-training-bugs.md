### [2026-08-19 lumen-gaf-vs-overlap-grad-reduce]
- Symptom: enabling `--lumen-gradient-accumulation-fusion` on Qwen3-8B MXFP4 (8×MI350X, `--overlap-grad-reduce` on) dies in the first backward on all ranks: `AssertionError: param.grad being None is not safe when overlap_grad_reduce is True` (`distributed_data_parallel.py:456`).
- Cause: Lumen MXFP4 wgrad with GAF sets `grad_weight = None` after accumulating into `main_grad`, leaving `param.grad` unset. Megatron's overlap-grad-reduce DDP hook requires a non-None grad buffer to schedule the async reduce.
- Repro: `TRAIN_STEPS=25 LAUNCH=native EXTRA_ARGS="--lumen-gradient-accumulation-fusion" bash examples/qwen3/run_pretrain_qwen3_8b_mxfp4.sh` → fails step 1. Baseline without the flag runs.
- Expected payoff if fixed: training report §5.5 estimates ~370 ms/step from `CUDAFunctor_add<float>` grad accumulation — largest single kernel in both Lumen and TE traces. Not MXFP4-specific; would help all precisions.
- Fix under test: `_gaf_placeholder_wgrad` in `lumen/ops/quantize/linear.py` now returns a shared zero buffer instead of `None` and sets `weight.grad_added_to_main_grad = True`, which is what `megatron/core/tensor_parallel/layers.py:573-602` does in the same spot. The DDP post-hook then passes its assert, skips its own `main_grad.add_`, and still registers the bucket ready. Applied to the five immediate wgrad sites only.
- Deliberately not applied to the `delay_wgrad` sites: a deferred wgrad reaches `main_grad` after the backward graph, so a placeholder there would let the reduce fire before the gradient exists. That three-way combination now raises a clear error in `lumen/models/megatron.py` instead of the Megatron assert. `delay_wgrad` defaults to off, so this does not affect the benchmark path.
- Verified: 30-step Qwen3-8B MXFP4 with `--lumen-gradient-accumulation-fusion` **and** `--overlap-grad-reduce` now completes 30/30, zero NaN/skipped. The assert is gone.
- The payoff is negative, not the estimated ~370 ms: median of iterations 16-30 is 6233.6 ms with GAF vs 6099.7 ms without, i.e. **134 ms slower (-2.15%)**. Loss tracks the non-GAF arm (identical to iteration 2, 1.5e-3 apart at iteration 30; a 0.44 mid-run excursion that reconverges, consistent with reorder noise on this high-lr mock run rather than a dropped or corrupted wgrad — the placeholder is zero-filled so it cannot corrupt).
- Why: Lumen's GAF is not fused. It computes `grad_weight` and then does a separate `main_grad.add_(grad_weight)` — the same `CUDAFunctor_add` the DDP hook would have done, just moved earlier in the backward where it serialises against dgrad. No add is eliminated, so the report's ~370 ms was never reachable through this flag.
- The ~370 ms premise itself is wrong, and the fused-epilogue follow-up is dead. Measured on gfx950 (`scripts/bench_wgrad_accum_tradeoff.py`):
  - The `main_grad(fp32) += wgrad(bf16)` add costs **94.1 ms/step** over the 31 MXFP4 layers (~109 ms if the 5 bf16 layers are included), not 370 ms, and it runs at 4.6-6.1 TB/s, i.e. already at HBM roofline. A perfect fused epilogue still has to read and write fp32 `main_grad`, so it moves 8 bytes/param instead of 12 — at most ~30 ms/step is recoverable, not 370.
  - `gemm_a4w4_asm` cannot fuse it regardless. All 30+ `hsa/gfx950/f4gemm/*.co` are bf16-out, an fp32 `out` is refused at `asm_gemm_a4w4.cu:176`, and the `D = alpha*A*B + beta*C` in its header is **not implemented**: `scripts/probe_a4w4_asm_beta.py` shows that with any C and `beta=1.0` the result matches `A@B` alone to 0.0031 (the MXFP4 noise floor) rather than `A@B + C` (0.03). The struct field exists, the assembly ignores it.
  - The source-compiled backends that could carry a fused epilogue are far too slow at the wgrad shapes: per-step wgrad GEMM totals are asm 392.8 ms vs CK 1157.8 ms. Fusing on CK spends 765 ms to save 94. The Triton a4w4 path has no tuned config for these shapes, and autotune already prefers asm on all 11 shapes in `mxfp4_autotune_qwen3_8b.json`.
- Status: closed. The crash fix is kept (the flag combination is legal now), but the GAF flag is not worth enabling on this config, and grad-accumulation fusion is not a route to a meaningful MXFP4 win on gfx950 without new AMD assembly.

### [2026-08-19 qwen3-8b-mxfp4-kernel-ranking-remeasured]
- Why: the MXFP4 training report §5.5 kernel table is the basis for most remaining optimization estimates, and its headline follow-up (gradient-accumulation fusion, "~370 ms/step") did not survive measurement. Re-ranked from a fresh trace rather than quoting it.
- Method: `TRAIN_STEPS=22 EXTRA_ARGS="--profile --use-pytorch-profiler --profile-step-start 18 --profile-step-end 20 --profile-ranks 0 --tensorboard-dir ..."`, aggregated with `scripts/summarize_torch_trace.py`. Summary kept at `examples/qwen3/results/prof_head/kernel_summary.txt`; the 3.3 GB trace was deleted (disk at 94%).
- Trace covers 2 training iterations, confirmed by fmha_bwd at 288 calls/iter = 36 layers x 8 micro-batches. Absolute ms are inflated ~20% (profiler stretched one of the two iterations: Megatron reported 6127 ms for iteration 19 against 7342 ms/iter of stream-0/1 busy time), so **treat the shares, not the absolute values, as the result**.
- The main compute stream is busy 7342 of ~7314 ms/iter, i.e. essentially 100% occupied, with only 718 ms on the comm stream. There is no idle slack to reclaim; anything removed from that stream shortens the step.
- Ranking by share of compute-stream busy time: attention 27.8% (fmha_bwd alone 18.4%, the largest single kernel), fp4 GEMM 20.2%, **bf16 Tensile GEMM 19.5%**, grad accumulate 10.1%, quantize/layout 7.8% (dual_layout 5.5%), optimizer 7.1% *in 9992 calls/iter*, norm 4.6%, activation 4.3%, rope 3.0%.
- Three things this changes: (1) attention is the single biggest cost and is pure bf16, so no MXFP4 work touches it; (2) bf16 Tensile GEMMs cost nearly as much as every MXFP4 GEMM combined despite covering only the 5 bf16 tail layers plus embedding/vocab — the shape attribution is not yet confirmed, but shrinking `TAIL_BF16` is the obvious next lever to measure; (3) the optimizer is launch-bound at ~10k kernels/iter.
- Not comparable to §5.5 term by term: that table is from a **global batch 32** job (2 micro-batches per rank, ~2007 ms/step), this run is global batch 128 (8 per rank, 6100 ms/step). The two agree once that is accounted for — §5.5 reports 586 `CUDAFunctor_add` calls/step at 2 micro-batches and this trace has 2344 at 8, both 293 params. What does not survive is the *estimate* built on it: report item 9 calls gradient-accumulation fusion "~370 ms/step, the largest single optimization available", and that is wrong for a reason independent of batch size (see the entry above).
- `TAIL_BF16` sweep result: `TAIL_BF16=0` (all 36 layers MXFP4) runs at **5711.0 ms/step vs 6099.7 ms baseline, i.e. 389 ms / 6.8% faster** (median of iterations 16-30, 30/30 completed, zero NaN, zero skipped). This confirms the bf16 tail layers, not the vocab projection, are the bulk of the bf16 Tensile GEMM share, and it is the largest single win measured in this whole round — larger than every remaining item on the optimization list.
- Full sweep (30 steps each, median of iterations 16-30, zero NaN and zero skipped in all six arms):

  | `TAIL_BF16` | MXFP4 layers | ms/step | vs base | speedup | marginal ms for that layer | loss@30 |
  |---|---|---|---|---|---|---|
  | 5 | 31 | 6099.7 | — | 1.000x | — | 2.361308 |
  | 4 | 32 | 6014.3 | −85.4 | 1.014x | 85.4 | 2.354551 |
  | 3 | 33 | 5946.3 | −153.4 | 1.026x | 68.0 | 2.365215 |
  | 2 | 34 | 5889.7 | −210.0 | 1.036x | 56.6 | 2.341842 |
  | 1 | 35 | 5841.8 | −257.9 | 1.044x | 47.9 | 2.346798 |
  | 0 | 36 | 5711.0 | −388.7 | 1.068x | 130.8 | 2.365570 |

- There is no cheap knee: the gain is close to linear, so a partial rollback of the bf16 tail buys a proportional share and nothing more. The marginal saving per converted layer runs 85.4, 68.0, 56.6, 47.9 and then jumps to 130.8 for the final layer (index 35).
- That jump is not `--first-last-layers-bf16` going inert at 0. `train_pretrain.sh:274-276` passes the flag unconditionally, and at `bf16_start = bf16_end = 0` the predicate in `lumen/quantize/__init__.py:238` simply selects no layers, so the code path is identical.
- **Position is not the explanation.** Two swaps at fixed layer count disagree in sign: with 1 bf16 layer, start is 40.9 ms *faster* than end (5800.9 vs 5841.8); with 5 bf16 layers, start is 38.6 ms *slower* (6138.3 vs 6099.7). (The first attempt at the 5-layer arm read 8157.8 ms and was measuring the prefix-matching bug below, not position; the number here is the re-run after the fix, verified at 124 quantized / 20 BF16.)
- **Run-to-run noise is 54 ms, which invalidates the marginal column.** Three runs of the identical `TAIL_BF16=0` config give 5711.0 / 5701.6 / 5756.0 ms — spread 54.4 ms, stdev 29.1. The earlier ~3 ms estimate came from two runs of the *same* config that happened to land close together. Every marginal value in the table (47.9 to 85.4) is within one to two stdev of the others, so the monotone decline and the 130.8 ms jump at the final layer are both noise artifacts, as are the ~40 ms position effects. Do not read per-layer structure out of single runs at this noise level.
- What survives: the endpoint. `TAIL_BF16=5` at 6099.7 ms vs the three-run mean of 5722.9 ms is **376.8 ms / 6.58%**, roughly 13 stdev out. The progression from 5 to 0 is monotone with steps averaging ~75 ms per layer and no evidence of a knee, so a partial rollback still looks proportional — but that is now a statement about linearity, not about the individual values.
- Not a recommendation to change the default. `TAIL_BF16=5` is an accuracy setting, and 30 steps on mock data says nothing about accuracy: the loss trajectories diverge mid-run (10.2 vs 9.4 at iteration 6, 6.3 vs 11.9 at iteration 10) and only reconverge by iteration 30 (2.3656 vs 2.3613). Flipping it needs a real C4 held-out comparison at the length the report uses, plus a sweep of the intermediate values (4, 3, 2, 1) to find where accuracy actually breaks.
- Status: measured. The accuracy side, and a per-layer re-measurement at a noise level that can actually resolve it, are in the 2026-08-24 C4 entry below.

### [2026-08-20 bf16-skip-prefix-matches-sibling-layers]
- Symptom: found while testing whether the bf16 tail's position matters. `--num-layers-at-start-in-bf16 5 --num-layers-at-end-in-bf16 0` on Qwen3-8B (36 layers) ran at 8157.8 ms/step against 6099.7 for the default, and the log gives it away: `Enabled FP8 (scaling=mxfp4) on 20 Lumen parallel linear modules, 124 left in BF16` — the precision assignment is inverted, 31 layers in BF16 and 5 in MXFP4.
- Cause: `_build_bf16_skip_prefixes` returns layer module paths ending in an index (`decoder.layers.1`), and both consumers tested membership with a bare `name.startswith(p)`. `decoder.layers.1` therefore also prefixes `decoder.layers.10` through `.19`. Skipping layers 0-4 actually skips {0..4} u {10..19} u {20..29} u {30..35} = 31 layers = 124 modules, which matches the log exactly.
- Silent, and only for some configurations. A tail of 5 in 36 layers is indices 31-35, none of which prefixes another index, so the default recipe and every ablation arm are unaffected. But any `--num-layers-at-start-in-bf16 >= 2` on a model with 10 or more layers mis-assigns precision: 2 requested on 36 layers puts 12 layers in BF16, with nothing in the log to suggest the request was not honoured.
- Fix: `is_under_bf16_prefix` in `lumen/quantize/__init__.py` requires the module boundary (`name == p or name.startswith(p + ".")`); used from both `_patch_linear_layers` and `enable_fp8_for_parallel_linear`. Unit-checked against the `.1` vs `.10`-`.19` collision.
- Status: fixed. The position experiment that exposed it is being re-run; its earlier 8157.8 ms reading measured the bug, not the position.

### [2026-08-24 native-mxfp4-weight-cache-gap]
- Symptom: a fresh two-iteration Qwen3-8B MXFP4 trace on the native-linear default shows `_convert_to_mxfp4_kernel` and `_transpose_packed_fp4_kernel` each at **992 calls / 62.5 and 71.3 ms per step**. 992 is exactly 124 MXFP4 linears x 8 micro-batches. Trace correlation binds both kernels to `QuantizedLinearFunction` forward with a BF16 weight input.
- Repro/profile: `TRAIN_STEPS=22 TAIL_BF16=5 LAUNCH=native EXTRA_ARGS="--profile --use-pytorch-profiler --profile-step-start 18 --profile-step-end 20 --profile-ranks 0 --tensorboard-dir .../prof_current_tail5"`. Summary: `examples/qwen3/results/prof_current_tail5/kernel_summary.txt`. It reproduces the 8/19 profile to within 1% (dual-layout 408.7 vs 406.8 ms, FP4 GEMM 1483.2 vs 1484.8), so this is not a one-off trace artifact.
- Cause: `_mxfp4_cached_weight` was only wired from `quantize._replace_forward`, the patched-Megatron linear path. `--lumen-linear` became the default later; native `parallel_linear._do_gemm` called `quantized_linear` with the BF16 weight and never supplied `fp8_weight_cache`, so the existing cache and its optimizer-step invalidation hook had nothing to cache. This also explains why report §5.13 measured the old cache toggle as −2.2 ms noise: that toggle did not reach the path being measured.
- Fix under test: native `_do_gemm` calls the existing `_mxfp4_cached_weight`, storing the cache on the Parameter, and passes its data/scale through `fp8_weight_cache` / `fp8_weight_scale` so `QuantizedLinearFunction` still computes wgrad for the BF16 master. `register_mxfp4_weight_optimizer_hooks` now clears both module-owned (patched path) and Parameter-owned (native path) caches after `optimizer.step()`.
- Structural verification: second trace at `examples/qwen3/results/prof_native_weight_cache/kernel_summary.txt` reduces convert and transpose from 992 calls each to **124 calls each** (one per linear per optimizer step), 62.5→4.3 and 71.3→4.8 ms. Quantize/layout falls 575.2→454.3 ms and compute-stream busy 7338.9→7246.6 ms. The profiler inflates the step, so use those as attribution only.
- Unprofiled A/B: 60 steps each, same code and mock corpus, cache off via `LUMEN_MXFP4_DISABLE_WEIGHT_CACHE=1`, median/mean over steps 21–60: off 6093.3/6104.2 ms, on **6019.9/6040.8 ms**, i.e. median **−73.5 ms / 1.21%**. Both zero NaN/skipped; loss@60 2.27216 / 2.27040. Memory rises from ~0.6387 to ~0.6498 of a 251.7-GiB GPU, about **2.8 GiB/GPU**, for both packed weight layouts and scales.
- Tests: `PYTHONPATH=/home/xdai/Lumen pytest -q tests/quantize/test_mxfp4_weight_cache_hook.py` -> 6 passed; added native Parameter-cache invalidation coverage. The recurring torch weakref shutdown traceback appears after pytest exits but does not change its zero exit code.
- Next target from the post-fix trace: `_dual_layout_quant_mxfp4_kernel`, 412.5 ms/step and 2976 calls over two iterations. It is now the largest MXFP4-owned non-GEMM kernel. §5.11 already ruled out memory traffic as the limiter; use the CUDA-event harness to sweep register pressure / tile occupancy. Do not revisit GAF: the 8/19 entry bounds its recoverable headroom and rules out the available ASM epilogue path.
- Status: fixed and measured; report §5.15.

### [2026-08-25 profiling-window-includes-a-validation-pass]
- Symptom: in every Qwen3-8B trace taken so far, forward-side kernels run at exactly twice their closed-form training count while backward-side kernels are correct. `fmha_fwd` 576 vs `fmha_bwd` 288 (= 36 layers x 8 micro-batches); FP4 GEMM 3968 where fwd+dgrad+wgrad is 3 x 992; `_dual_layout_quant_mxfp4_kernel` 2976 where fwd+bwd is 2 x 992; forward RMSNorm and rope likewise doubled, their backward counterparts not.

A targeted gfx950 test matches PyTorch bit-for-bit for row and transposed outputs for both OCP dtypes and matches amax.
